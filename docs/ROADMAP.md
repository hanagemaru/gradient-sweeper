## 1. 盤面の描画刷新（完了）

### 症状

- マスを開けるときの動作が重い
- 異なる隣接状態が同じ色で表示され、推理が成立しない場面があった

### 原因

**重さの主犯はPNGタイルではなく、タイマーによる常時再レンダーだった。**

`src/hooks/useTimer.ts` が100ms間隔で `setElapsedMs` を呼び、その state が `/game` ページ本体にあった。
同じコンポーネントが `<Board>` を描いていたため、毎秒10回、81セル分の差分計算が走り続けていた。
タップの重さはこの常時負荷の上に乗っていた。

**色の潰れ**は `getIceAsset()` の写像の問題。45通りの隣接状態が11種類のタイルにしか分かれておらず、
`ice-red-4` と `ice-blue-4` はそれぞれ13状態を兼ね、`ice-mix-1` / `ice-mix-3` は一度も描画されなかった。
経緯と当時の対応表は `docs/technical/COLOR-MAPPING.md` に残してある。

### 実施した対策

**色**（`src/lib/ice-colors.ts`）

45状態すべてに異なる色を与える写像を OKLCH で構成した。

- 色相 = 赤青の比率（純青 → 紫 → 純赤）。比率が同じなら合計数が変わっても色相は同じ
- 明度と彩度 = 合計数。増えるほど暗く鮮やかになる
- 彩度の切り詰めは個別の色相ではなく**色相の弧全体**で行う。
  色相ごとに削れ方が違うと、同じ合計数なのに青だけくすむ
- 青端・赤端・最も暗い帯の明度は、「弧全体で同じ彩度を出せる」制約のもとで
  隣接色差が最大になる点を総当たりで選んだ（262° / 30° / L=0.50）

**描画**（`src/components/game/Cell.tsx`, `src/lib/tile-masks.ts`）

45色ぶんのPNGを描くのではなく、下絵をグレースケールで持ち色はコード側で塗る。

- 下絵は既存タイルから抽出した5枚のみ（`scripts/extract-tile-masks.mjs`）
- 各マスクは平均が中間グレー。`mix-blend-mode: overlay` で明るさを変えずに質感だけ乗せる。
  パレットは明るさで爆弾の数を表すので、この性質が前提になる
- セルあたりの画像は1枚

**パフォーマンス**

- タイマー表示を `TimerDisplay` に切り出し、経過時間の state をその中に閉じ込めた。
  親は `elapsedRef` を読むだけなので、100ms ごとの更新で再描画されない
- `Cell` を `React.memo` 化

Playwright で実測し、**タイマー稼働中2秒間の盤面のDOM変化が 0** であることを確認済み。

### 見送ったもの

- **`cloneBoard` の copy-on-write 化。**
  `revealCell` がセルを直接書き換える設計なので、座標ベースへの作り直しが必要になる。
  自動テストが無い状態で連鎖開放のロジックに手を入れるのは危険度が高い。
  上記の対策で常時負荷は消えており、タップ1回あたりの再描画は
  軽量な要素になった今は無視できるコストなので、必要になってから行う
- `public/assets/frostbound/tiles-v5/ui-button.png` の圧縮（100KB。他のタイルは約1.5KB）
- **下絵の8段階への描き分け。** 現在は4段階を合計2つずつに割り当てている。
  下絵は「だいたいの密度」だけを担い、正確な内訳は色が担う設計なので、
  8段階に増やしても色が持つ明度の情報と重複する。実機で物足りなければ後から足す

### 実装済み: マスを開けたときの飛散演出

マインクラフトのブロック破壊のような、タイルの色を拾った小さい四角が放物線で飛ぶ演出。

`TileBurst` が盤面の上に `<canvas>` を1枚重ね、連鎖開放でもDOM要素を増やさずに描画する。

## 2. UI全面のピクセル化

### 症状

ゲーム画面以外（ホーム、TA難易度選択、リザルト、ランキング）にピクセル感がなく、
汎用的な Tailwind グラデーションのまま。世界観が分断されている。

### 現状

- 全ページが `PixelScene` の固定キャンバスに載り、グレイシャーテーマとピクセルUIを共有する
- 日本語は DotGothic16、英数字は VT323 を使用する
- 盤面の赤／青爆弾は専用ピクセルPNGを使用する（PR #20）
- `/style-lab` と子ルートをデザインの基準として使える

### 実施結果と残作業

C案（ARCADE CABINET）を基準に共通のピクセルUIを整備し、各ページへ展開済み。
爆弾アセット・アイコン・セル内の影だけに変更を限定したPR #20も完了し、
ゲームロジックや全体CSSへ影響させずに盤面の絵文字を解消した。

## 3. 収益化

### 現状

`src/lib/rewarded-provider.ts` は**モック実装**。リバイブの導線（`GameOverModal`）だけ先にできている。

### 検討材料

- Web PWA はネイティブ向けのリワード広告SDK（AdMob等）が使えないため、選択肢が限られる。
  **実施可否と規約適合の調査を独立タスクとして立てること。** 実装を始める前に調べる
- 広告を入れる前に継続率（ランキング、実績、デイリーチャレンジ等）を上げる方が費用対効果が高い
- リワード型は導線が既にあるので、広告手段さえ決まれば差し替えは小さい
