# ロードマップ

最終更新: 2026-08-11

現時点で認識している課題と、着手順の方針をまとめる。
各項目は独立したブランチ・独立したPRで進める（AGENTS.md の「1タスク1ブランチ」に従う）。

## 着手順

順序に意味があるのは 1 と 2 と 3 で、いずれも `src/components/game/Cell.tsx` を触るため。
並行して進めるとコンフリクトする。

| 順 | タスク | 理由 |
|---|---|---|
| 1 | パフォーマンス改善 | 体験への影響が最も大きい。先に描画構造を整えてから見た目を変える方が手戻りが少ない |
| 2 | 色マッピングの再設計 | ゲーム性の根幹。1 で `Cell` の描画方式が変わるのでその後 |
| 3 | UI全面のピクセル化 | 範囲が広い。1・2 が固まってから着手する |
| 4 | 収益化（広告） | UI が固まらないと配置が決められない |

テスト整備は上記のどこにも属さないが、**1 に着手する前に最低限のゲームロジックのテストがあると安全**。
`generateBoard` / `revealCell` / `checkWin` の3つだけでも入れておくと、以降の変更で回帰を検出できる。

## 1. パフォーマンス改善

### 症状

マスを開けるときの動作が重い。

### 原因（コード調査済み）

主犯は PNG タイルではなく**タイマーによる常時再レンダー**。

`src/hooks/useTimer.ts` が 100ms 間隔で `setElapsedMs` を呼び、その state が `/game` ページ本体
（`src/app/game/page.tsx`）にある。同じコンポーネントが `<Board>` を描いているため、
**毎秒10回、81セル × 各2〜3個の `next/image` 要素の差分計算が、何もしていなくても走り続けている。**
タップの重さはこの常時負荷の上に乗っているので体感が悪化する。

副次要因:

- `cloneBoard`（`src/lib/game-logic.ts`）が開放のたびに81セル全部を新オブジェクトにするため、
  `React.memo` を入れただけでは開放時の全再レンダーは防げない
- `unoptimized` 指定なら `next/image` の利点はゼロで、コンポーネントのオーバーヘッドだけ残る
- `public/assets/frostbound/tiles-v5/ui-button.png` が 100KB（他のタイルは約1.5KB）

### 対策（効く順）

1. タイマー表示を独立コンポーネントに切り出し、state を局所化する（**これが一番効く**）
2. `Cell` を `React.memo` 化する
3. `cloneBoard` を copy-on-write にする（変更されたセルだけ新オブジェクトにする）
4. `next/image` を素の `<img>` か CSS `background-image` に置き換える。
   さらに詰めるならタイルをスプライトシート1枚にまとめて `background-position` で切り出す
5. `ui-button.png` を圧縮する

### マスを開けたときの飛散演出

マインクラフトのブロック破壊のような、タイルの色を拾った小さい四角が放物線で飛ぶ演出。

**実装制約**: パーティクルを DOM 要素で作ると上記の問題を悪化させる。
盤面の上に `<canvas>` を1枚重ねて描画すること。DOM要素は1つも増えない。

## 2. 色マッピングの再設計

### 症状

マスの色の判別が難しい。

### 原因

`docs/technical/COLOR-MAPPING.md` に完全な対応表と分析がある。要点:

- 45通りの (赤, 青) 状態が **11種類のタイルにしか分かれていない**
- `ice-red-4` と `ice-blue-4` がそれぞれ13状態を兼ねている（赤4個以上は全部同じ絵）
- `ice-mix-1` と `ice-mix-3` は**一度も描画されない**（mixは実質2段階しかない）
- `赤1青3` と `赤0青4` が同じ絵になり、混色情報が失われる

### 進め方

1. 実タイル画像を並べた比較ページでユーザーが「判別が厳しい組み合わせ」を特定する（済 / 別途共有）
2. その結果を受けて `getIceAsset()` の写像を再設計する
3. 必要なアセットを追加する（`tiles-v5` の枠内で追加するか、`tiles-v6` を立てるかは要判断）
4. `docs/technical/COLOR-MAPPING.md` の表を**実装から再生成**して更新する

### 検討の軸

- `level` の上限4を上げるか、それとも合計数ではなく別の指標にするか
- 2倍しきい値によるトーン判定を、より段階的な比率表現に変えるか
- 色以外の手がかり（模様・アイコン・輪郭）を足すか。色覚特性への配慮としても有効

## 3. UI全面のピクセル化

### 症状

ゲーム画面以外（ホーム、TA難易度選択、リザルト、ランキング）にピクセル感がなく、
汎用的な Tailwind グラデーションのまま。世界観が分断されている。

### 現状

- グレイシャーテーマが当たっているのは `/game` のみ
- フォントは VT323（`@fontsource/vt323`）で全体に適用済み。この方向性は維持する
- `src/components/Icon.tsx` はまだ絵文字のプレースホルダー
- `/style-lab` に既存のタイル見本ページがあり、デザインの基準として使える

### 進め方

方向性（レトロゲーム機風 / ドット絵アドベンチャー風 など）をユーザーが選んでから着手する。
決まったら共通のピクセルUIコンポーネント（ボタン、パネル、モーダル）を先に作り、
各ページをそれで置き換える。ページごとに個別CSSを書くと破綻する。

## 4. 収益化

### 現状

`src/lib/rewarded-provider.ts` は**モック実装**。リバイブの導線（`GameOverModal`）だけ先にできている。

### 検討材料

- Web PWA はネイティブ向けのリワード広告SDK（AdMob等）が使えないため、選択肢が限られる。
  **実施可否と規約適合の調査を独立タスクとして立てること。** 実装を始める前に調べる
- 広告を入れる前に継続率（ランキング、実績、デイリーチャレンジ等）を上げる方が費用対効果が高い
- リバイブ報酬型は導線が既にあるので、広告手段さえ決まれば差し替えは小さい

## リスク・技術的負債

| 項目 | 内容 | 影響 |
|---|---|---|
| テスト0件 | 自動テストが1つも無い。CI は lint と build のみ | 全変更が回帰リスクを持つ |
| スコアの改ざん可能性 | Endless のスコアはクライアント申告そのまま。`src/app/api/score/route.ts` の検証は `score >= 0` のみ | ランキングの信頼性 |
| RLS 未有効 | Supabase の Row Level Security が未設定（`docs/DEPLOYMENT.md`） | サービスロールキー漏洩時の被害範囲 |
| 依存の脆弱性 | `npm audit --omit=dev` で high 3件（`postcss` / `sharp`）。解消には Next.js 16 へのメジャー更新が必要 | 別タスクとして計画済み |
| 初手保証なし | `generateBoard` は入力前に盤面を確定するため、最初のタップで爆発しうる | ゲーム体験。仕様として意図的かは要確認 |
