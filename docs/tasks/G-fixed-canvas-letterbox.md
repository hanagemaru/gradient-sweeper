>   `transform: scale(min(...))` だけで完結している。

## 目的

現在の「ビューポート追従カメラ」方式をやめて、スマホ向けの**固定解像度キャンバス**を
1つ作り、横長画面は左右を、縦長画面は上下を黒く切る（レターボックス／ピラーボックス）
方式に転換すべきかを検討し、方向性が決まれば実装する。

**このタスクはまず検討から始める。いきなり実装しないこと。**

## 背景

PR #10（レーンB）で、ホーム・難易度選択・リザルト・ランキングの背景を
「画面より大きい1枚の背景ワールードを、ビューポート固定のカメラで覗く」方式にした
（`docs/tasks/B-pixel-ui.md` の「背景ワールド実装時に確定したこと」参照）。
この方式は `docs/tasks/B-pixel-ui.md` に明記した決定
（「大きな画面では見える範囲を広げる」）に基づいている。

この方式には代償がある。パネル（`.stack`）の位置は `.content` の
`padding-top: clamp(92px, 15vh, 132px)` 経由でビューポート高さに依存するため、
**ワールド座標上でのパネル位置がスマホ5サイズでバラバラに動く**。
直近の作業（クリスタルをパネル上下に見せる）では、これが原因で
「全機種共通で使える『パネルの上』の帯が存在しない」という幾何学的な制約に当たり、
`CRYSTAL_SLOTS` を機種レンジ別に2〜3枠へ分けることで回避した
（詳細は `docs/tasks/B-pixel-ui.md` 該当箇所とスクリプト内コメント）。

固定解像度キャンバス＋レターボックスにすれば、この種の「ビューポート依存の座標計算」が
根本から消える。パネルも背景も1つの固定サイズの中で完結するため、以後の配置調整が
大幅に楽になる。ただし以下のトレードオフがある。

- `docs/tasks/B-pixel-ui.md` に明記済みの決定（大画面ほど世界が広く見える）と矛盾する。
  タブレット・PCでは今より見える範囲が狭くなる（同じ絵を拡大表示するだけになる）。
- スコープが背景だけでは収まらない。パネル幅・フォントサイズ・padding が
  `clamp()` などビューポート相対値なので、固定キャンバス化するなら
  `pixel-ui.module.css` 全体（共通コンポーネント含む）の設計を変えることになる。
- `image-rendering: pixelated` はスケール倍率が非整数だと滲み・シマーが出やすい。
  CSS `transform: scale()` で滑らかに拡大するか、整数倍にステップで丸めて余白を
  太らせるか、方針を決める必要がある。

## 前提となる知識

- `.backdrop`（`position: fixed`, ビューポート全面）が「カメラ」。
  `.world`（`position: absolute; top/left: 50%; translate: -50% -50%`）が
  ワールド本体で、常に画面中央基準。ワールド寸法は 2880x1620、横方向に2回タイリング
  （タイル幅1440）。詳細・理由は `src/components/ui/pixel-ui.module.css` の
  `.backdrop` / `.world` 直前のコメントと `docs/tasks/B-pixel-ui.md` にある。
- 配置定義は `scripts/generate-background-world.mjs` が
  `src/lib/background-world.ts` へ静的生成する。乱数は seed 固定でビルド時に1回だけ。
- パネル関連の主要な可変値は `src/components/ui/pixel-ui.module.css` の
  `.content`（`padding-top: clamp(92px, 15vh, 132px)`）と `.stack` / `.stackMenu` /
  `.stackWide`（ページごとに `max-width` が異なる: home/ta=320, result=350, ranking=440）。
- 不透明部分とPNG矩形がズレる問題（クリスタルPNGは絵が下寄りで上に透明余白がある）に
  一度ハマっているので、再実装時も同じ轍を踏まないこと。
  `docs/tasks/B-pixel-ui.md` の該当箇所を先に読むこと。

## やること

### 1. まず実装しない。トレードオフを整理してユーザーに選んでもらう

最低限、次を具体案として詰めること。

- 基準解像度は何にするか（例: 390x844 など、対象スマホの中間的なサイズ）
- スケーリングは整数倍のみに丸めるか、`transform: scale()` で滑らかに拡大するか
  （`image-rendering: pixelated` との相性）
- レターボックス部分は単色の黒か、それとも背景ワールドの続きを覗かせるのか
- タブレット・PCで「広く見える」体験を失うことを許容するか
- 固定キャンバスに含める範囲は背景だけか、UIコンポーネント（パネル幅・フォント・padding）
  も含めるのか

2〜3案、トレードオフ付きで提示し、ユーザーの承認を得てから実装へ進むこと。
（`docs/tasks/B-pixel-ui.md` 冒頭の「着手前にユーザーが方向性を選ぶ必要がある」と同じ進め方）

### 2. 方向性が決まったら実装する

既存のワールド生成・キープアウト計算（`UI_KEEPOUT`, `CRYSTAL_SLOTS` など）は
固定キャンバス化によって前提が変わるため、素材の再配置ロジックごと見直しが必要になる。
座標系の単純化が主目的なので、可能な限りビューポート依存の計算を削ぎ落とす方向で進める。
