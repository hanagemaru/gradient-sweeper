# C: スコアのサーバー側検証

## 目的

ランキングに登録されるスコアが、実際のプレイと矛盾していないかをサーバー側で確かめる。

## 背景

現在 Endless のスコアは**クライアントの申告をそのまま保存している**。
`src/app/api/score/route.ts` の検証は `score >= 0` だけで、
ブラウザの開発者ツールから任意の値を送れば1位になれる。

Supabase の RLS も未設定（`docs/DEPLOYMENT.md` に記載）。

## 前提となる知識

スコアの計算式は `src/hooks/useGame.ts` の reducer にある。

- セル開放: `開いたセル数 × SCORE_PER_CELL × レベル`
- スピードボーナス: 前回開放から `SPEED_BONUS_THRESHOLD_MS` 以内なら
  コンボ倍率（0.5 / 1.0 / 1.5 / 2.0）を掛けた分を加算
- レベルクリア: `LEVEL_CLEAR_BONUS × レベル`、ノーミスならさらに同額
- 被弾: `MISS_PENALTY` を減算（0が下限）

定数は `src/types/game.ts` にある。

Time Attack は `score` カラムに**最終タイム(ms)** を入れている（小さいほど上位）。
Endless とは意味が違うので、検証も別々に考える必要がある。

## 触ってよいファイル

- `src/app/api/score/route.ts`
- `src/app/api/leaderboard/route.ts`
- `src/lib/score.ts`
- `src/lib/supabase.ts`
- 新規の検証ロジック（`src/lib/` 配下）
- `docs/DEPLOYMENT.md` の RLS に関する記述

## 触ってはいけないファイル

- **`src/hooks/useGame.ts` と `src/types/game.ts`** — スコアの計算式そのものは変えない。
  変えると既存のランキングと互換性がなくなる
- `src/components/game/` 配下 — レーンAの担当
- `src/app/page.tsx`, `ta/`, `result/`, `ranking/` — レーンBの担当
- `docs/PROJECT-STATUS.md`, `docs/ROADMAP.md` — 全レーン共通で編集禁止

## やること

**完全な検証は原理的に不可能**なので、上限を設けて明らかな不正を弾く方針にする。

1. **理論上の最大スコアを求める。** レベルとプレイ時間から、
   全セルをスピードボーナス最大で開き続けた場合の上限を計算し、それを超える値は拒否する
2. **項目間の整合を確認する。** 例えば
   - ミス回数が多いのにスコアが最大値に近い
   - レベルが低いのにスコアが大きすぎる
   - Time Attack の最終タイムが、その難易度で物理的に不可能なほど短い
3. **レート制限を永続化するか検討する。**
   現在はメモリ上のIP単位（10回/分）なので、サーバーが再起動すると消える
4. **RLS の有効化を検討する。** サービスロールキーを使っているので今は動くが、
   キーが漏れたときの被害範囲が変わる

## 完了条件

- 明らかに不正な値が拒否される
- 正当なプレイのスコアが誤って拒否されない（ここを外すと実害が大きい）
- 拒否した場合の応答が、クライアント側で適切に扱われる

## 注意

**誤検知のほうが害が大きい。** 正当なプレイヤーのスコアを弾くくらいなら、
多少の不正を通すほうがましだと考えて上限を設定すること。
判断に迷う値は通してログに残す方針でよい。

## 検証

1. `npm run lint` と `npm run build` が通る
2. 正常なスコア・上限ぎりぎりのスコア・明らかに不正なスコアで、
   それぞれ期待通りの応答になることを確認する
3. Supabase 未設定でもビルドが通ること（モックにフォールバックする挙動を壊さない）
