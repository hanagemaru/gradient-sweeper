# I: 固定キャンバスの基準高さを実機ビューポートに合わせる

> **状態: 実装済み。ただし 670 は後続の PR #15 で 550 に変更された。**
>
> このレーン: 390x844 → **390x670**。倍率式の `dvh` → `svh`。
> その後 PR #15 で **390x550** へ。理由と検算は末尾
> 「[後続タスク2の結論: 550 へ詰めた](#後続タスク2の結論-550-へ詰めた)」を参照。
> 以下の本文は 670 当時の記録としてそのまま残してある。

## 目的

ホーム画面をスマホで開くと、キャンバスが画面幅の6割ほどに縮小され、左右に太い黒帯が
出る。基準解像度の高さが実機のブラウザに存在しない値だったので、実測に合わせて詰める。

## 背景

`src/components/ui/pixel-ui.module.css` の倍率式はこうなっていた。

```css
transform: scale(min(calc(100vw / 390px), calc(100dvh / 844px), 2.2));
```

左右に黒帯が出ない（＝横幅基準が選ばれる）条件は `dvh / vw >= 844/390 = 2.164`。

**`390x844` は iPhone 12〜14 の「画面」スペックであって、ブラウザのビューポートではない。**
ブラウザは上下のUIで 100〜190 CSS px を持っていくため、390px 幅の端末に 844px の高さは
存在しない。`viewport-fit=cover` も設定していないので、ホーム画面に追加した standalone
（`manifest.json` は `"display": "standalone"`）でも実効 763 程度・比 1.96 で届かない。

つまり左右の黒帯は特定機種の例外ではなく、**実機ブラウザでは常に出ていた**。
レーンG（`G-fixed-canvas-letterbox.md`）で基準解像度を「対象スマホ5機種の中央値」として
決めたときに、画面サイズとビューポートサイズを取り違えたのが原因。

### 高さを 670 にした根拠

充填率（不足する軸がビューポートを埋める割合）は `min(r/A, A/r)` で決まる。
r = ビューポート比 `svh/vw`、A = キャンバス比 `canvasH/390`。

実機ブラウザの r は2つの塊に分かれる（svh = ツールバー展開時の高さ）。

| 区分 | 代表機 | svh 実効 | r |
|---|---|---|---|
| iOS Safari 主力 | 390x844 / 414x896 / 430x932 | 664 / 716 / 752 | **1.70〜1.75** |
| iOS Safari 最小 | 375x667 (SE/8) | 553 | 1.47 |
| Android Chrome 主力 | 360x800 / 393x873 / 412x915 | 744 / 817 / 859 | **2.07〜2.08** |
| Android 旧 | 360x640 | 584 | 1.62 |

iOS の塊が 1.70〜1.75 に密集している。日本語タイトルなので iOS 比率が高い（国内で約6割）。
iOS 6割 / Android 4割で重み付けした期待充填率は次のとおりで、A を iOS の塊に
合わせる（`390 * 1.72 ≒ 670`）のが最大になる。

| A | canvasH | 期待充填率 | 最小機(1.47) | iOS主力(1.70) | Android(2.07) |
|---|---|---|---|---|---|
| 2.164（変更前） | 844 | 0.84 | 0.68 | 0.79 | 0.96 |
| 1.795 | 700 | 0.92 | 0.82 | 0.95 | 0.87 |
| **1.718（採用）** | **670** | **0.94** | **0.86** | **0.99** | **0.83** |

**Android は 0.96 → 0.83 に下がる**（横は埋まるが上下に黒帯が出る）。これは承知の上での
トレードオフで、台数の多い iOS 側の 0.79 → 0.99 で取り返している。

この方式では両軸を同時に埋めることは原理的にできない。比が一致した機種だけがぴったりに
なり、それ以外はどちらかの軸に必ず余白が出る。両方の塊を埋めたい場合は下記の強化案。

### `dvh` → `svh`

`dvh` はブラウザのツールバーが引っ込むと伸びるので、操作中にキャンバス全体の倍率が
変わる。`svh`（ツールバー展開時＝最小ビューポート）で組めば倍率は常に一定。

なお「ツールバーを畳ませて高さを稼ぐ」方向は**採らない**。iOS がツールバーを畳む条件は
ドキュメントがスクロールすることだけで、`.stage` が `position: fixed` の現構造では
そもそも発火しない。スクロールさせるのはゲームの性質上許容できないという判断があり、
仮に畳めても倍率が動いて不快になる。`svh` は「最小で組む」という宣言でもある。

## やったこと

- `pixel-ui.module.css`
  - `.scene` の `height: 844px` → `670px`、倍率式を `100dvh / 844px` → `100svh / 670px`
  - `.content` の `min-height: 844px` → `min-height: 100%`（キャンバス高さの二重管理をやめた）
  - 冒頭コメントに「なぜ 844 が不可能なのか」と充填率の根拠を残した
- `scripts/generate-background-world.mjs`
  - `WORLD_HEIGHT` 844 → 670
  - `CANVAS_UI_KEEPOUT.y1` 498 → **524**。ページごとにパネル下端が違うことが
    実測で分かったため（下記）
  - `CANVAS_BOTTOM_BANDS` を「2段＋44px空白」から「単一帯 + 中心を24px以上ずらす」へ
- `src/lib/background-world.ts` を再生成（シードは据え置き `SEED=20265786`）

### パネル下端の実測値（倍率1・ビューポート 390x670）

`.stack`（パネル＋言語トグル）の下端はページごとに違う。

| ページ | stack y |
|---|---|
| home | [120, 488] （パネル 120-423 + 言語トグル 437-488） |
| ranking | [120, 511] |
| ta | [120, 514] |
| result | [120, 626] |

キープアウト `y1` は result を除く最大（ta の 514）＋余裕10px = **524**。

### 下側クリスタルの帯が作り直しになった理由

レーンG の決定に「クリスタルは中途半端に半分だけパネルへ潜り込ませない
（完全に見えるか、完全にパネルの裏か）」がある。パネル下端が 488/511/514/626 の4つ
あるので、不透明部分がこのどれかをまたぐと半分潜り込みになる。

またがずに置ける帯は **y[524, 626] の 102px** しかない（下端 626 = result のパネル下端。
ここに収めれば home/ranking/ta では全部見え、result では全部パネルの裏に入る）。

844 のときは帯が 336px あり、上下2段に割って 44px の空白を強制できた。102px では
不透明部分の合計 129px（cluster-medium 84 + cluster-wide 45）すら入らないので、
段に割るのをやめ、**不透明部分の中心を 24px 以上ずらす**方式に変えた。横方向は帯幅
370px を `fits()` の `MIN_GAP` が使って離してくれる。

結果（採用シード）: 中心のずれ 30.5px、水平すきま 67px、半分潜り込みなし。

## 後続タスク2の結論: 550 へ詰めた

**PR #15 で 390x670 → 390x550 に変更した（比 1.718 → 1.410）。**

### 経緯

670 は「期待充填率の最大化」で選んだ値で、**iPhone SE (375x553) だけは高さ基準のまま**
左右に 26.6px ずつの黒帯が残っていた。実機（SE）で遊んだ結果
「キャンバスが画面幅に届かないので盤面が小さく操作しづらい」という指摘が出た。

そこで方針を**「対象の全機種で左右の黒帯を 0 にする」**に変えた。

### 検算

盤面は常に 324 キャンバス px（9 x 36px）。左右の黒帯が無い機種では
**盤面の画面比 = 324 / キャンバス幅**で、高さには依存しない。
つまり高さは「幅基準に落ちるかどうか」だけを決める。

左右の黒帯が出ない条件は `svh/vw >= canvasH/390`。対象機種の `svh/vw` の最小値は
SE の 553/375 = 1.475 なので `canvasH <= 575`。svh は推定値なので 24px の余裕を見て
**550**（必要 svh 529）にした。

| 機種 | 670 のとき | 550 のとき |
|---|---|---|
| iPhone SE 375x553 | 盤面 267px (71.3%) / 左右帯 26.6px | **盤面 312px (83.2%) / 左右帯 0** |
| iPhone 12 390x664 | 321px (82.3%) / 1.7px | 324px (83.1%) / 0 |
| iPhone XR 414x716 | 344px / 0 | 344px / 0 |
| Pro Max 430x752 | 357px / 0 | 357px / 0 |
| Android 360x744 | 299px / 0 | 299px / 0 |
| Pixel 412x859 | 342px / 0 | 342px / 0 |

**SE 以外は盤面の大きさが変わらない**（もともと幅基準だったため）。
代わりに上下の黒帯が増える（Pixel で片側 76 → 139px）。操作性には関係しないという
判断で受け入れた。

### 盤面をさらに大きくしたい場合

占有率 = 324 / キャンバス**幅**なので、幅を 390 → 360 にすれば全機種で 90.0% になる
（SE 338px、iPhone 12 351px）。ただし高さも比例して 508 まで下がるため、

- パネル下端がキャンバス下端に届き、**装飾を置く帯が消える**
- HUD 幅が 358 → 342 になりステータスカードが 80 → 76px

という代償がある。**今回は採らなかった。** 実施するなら背景ワールドの設計を
「パネルの左右へ寄せる」方向で作り直すことになる。

### 一緒に入った変更

- `.content` の padding `120px 16px 42px` → `98px 16px 34px`、
  `.contentOverlay` の padding 24 → 16（リザルトのオーバーレイが 4px はみ出すため）
- ゲーム画面の縦の固定分 576 → 501（`game.module.css` の冒頭コメントに内訳）。
  **盤面フレームの 342px だけは動かせない**ので、削ったのは上下余白・HUD・操作ボタン
- 背景ワールドを 390x550 で再生成、採用シード **6500**（可視セル 4/4）。
  `cluster-medium` は不透明 84px が上下どちらの帯（84px / 48px）にも収まらず**不採用**
- `game-scenery.ts` は 3個 → **1個**。盤面より下の y[493,550] の 57px しか空きがなく、
  そこは操作ボタンに左右へ分断されるため「横一線にしない」規則を満たす2個目が置けない

### 検証（実施済み）

Chromium で7機種 x 4ページ（home/ta/ranking/game）を実測。

- **左右の黒帯が全機種・全ページで 0px**
- ドキュメントの縦スクロール無し、キャンバス内スクロールも無し
  （直接URLアクセス用の `/result` フルページ版のみ 88px スクロールする。
  `.scroll` が受けるので背景と黒帯は動かない）
- タップ判定 0/81 不一致、スワイプのしきい値も4機種で全一致。
  `Board.tsx` は**無編集**で通った（PR #15 の `getScale()` が倍率を吸収するため）

- **未実施**: 実機での確認。エージェント環境からは `netlify.app` に到達できない。
  **SE の svh 553 は knowledge ベースの推定値なので、実機の SE で
  左右に黒帯が出ないことの確認だけは人手で必要。**
  出た場合は高さをさらに下げる（540 なら必要 svh 519）。盤面の大きさは変わらない。
