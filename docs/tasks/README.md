# タスク仕様

複数のセッションを同時に走らせるための仕様書置き場。

## 使い方

新しいセッションを始めるとき、次の一行だけを入力する。

```
docs/tasks/A-particles.md を読んで実装して
```

仕様書に目的・触ってよいファイル・完了条件が書いてあるので、
毎回長い指示を打ち込む必要がない。スマホから始めるときはこれが効く。

## 並行の原則

**タスクは機能ではなくファイルで分ける。**
コンフリクトはファイルの重なりからしか生まれない。
スマホではコンフリクト解消が特につらいので、そもそも起きない分け方にする。

## 全セッション共通のルール

1. **1タスク＝1ブランチ＝1PR。** 同じブランチに2セッションを当てない
   GitHubの `main` を正本とし、毎回最新の `origin/main` から新しいブランチを作る。
   ローカル `main` の継続的な同期や、別エージェントのローカル状態は前提にしない
2. **CodexとClaude Codeはブランチを分ける。** Codexは `codex/`、Claude Codeは
   `claude/` を使い、開始前にオープン中のPRと担当ファイルの重なりを確認する
3. **仕様書の「触ってはいけないファイル」を必ず守る。**
   自分のレーンの外に手を伸ばした瞬間、他のセッションと衝突する
4. **`docs/PROJECT-STATUS.md` と `docs/ROADMAP.md` は編集しない。**
   全セッションが更新すると必ずコンフリクトする。
   共有すべき内容があれば、PR説明か自分のタスク仕様に書く。
   これらの集約は全部マージし終えてから、単独のセッションで行う
5. **依存は勝手に追加しない。** `package-lock.json` は手で直せないので、
   必要になったら実装せずに報告すること
6. **緑になったらすぐマージ。** ブランチを長生きさせるほどコンフリクト率が上がる
7. 検証は `npm run lint`、`npm run test`、`npm run build`。すべて通ってから PR を出す
8. 見た目に関わる変更は Netlify のデプロイプレビューで確認する

## 仕様書の書き方

新しいタスクを足すときは既存のものに倣う。最低限これだけは書く。

- **目的** — 何のためか。判断に迷ったときの拠り所になる
- **背景** — なぜ今それをやるのか。調査済みの事実があれば書く
- **触ってよいファイル / 触ってはいけないファイル** — レーンの境界
- **やること** — 手順ではなく、達成すべき状態
- **完了条件** — 何をもって終わりとするか
- **検証** — どう確かめるか
