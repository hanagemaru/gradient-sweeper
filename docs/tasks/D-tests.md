# D: テスト整備

## 目的

ゲームの中核ロジックに自動テストを入れ、変更で壊れたことを検出できるようにする。

## 背景

**自動テストが1件も存在しない。** CI は `npm run lint` と `npm run build` だけで、
どちらもゲームの挙動が壊れたことを検出できない。

これが現時点で最大の技術的負債。実際、盤面の描画刷新のときに
`cloneBoard` の copy-on-write 化を「テストが無いので危険」という理由で見送っている。
テストが入れば、その手の改善に踏み込めるようになる。

## 同時実行の制約

**レーンE（Next.js 16 移行）と同時に走らせないこと。**
E は `package.json` を触るため衝突する。

**テストランナー（vitest）は導入済み**なので、このタスクで依存を追加する必要はない。
`package.json` を触らずに済むなら、A・B・F とは並行できる。

## 触ってよいファイル

- 新規・既存のテストファイル（`src/**/*.test.ts`）
- `vitest.config.mts`（設定の調整が必要な場合のみ）

**`package.json` と `package-lock.json` は触らないこと。**
必要な依存はすでに入っている。追加が要ると判断した場合は、実装せずに報告すること。

## 触ってはいけないファイル

- **テスト対象の実装コード。** テストを通すために実装を書き換えない。
  もし実装のバグを見つけたら、**直さずに報告する**。修正は別タスクにする
- `src/components/game/` 配下 — レーンAの担当
- `src/app/api/` 配下 — レーンCの担当
- `docs/PROJECT-STATUS.md`, `docs/ROADMAP.md` — 全レーン共通で編集禁止

## 現状

vitest が導入済みで、`npm test` で実行できる。CI でも走る。
`src/lib/game-logic.test.ts` に最小限のテスト（11件）が入っているので、これを土台に広げる。

環境は `node` で、jsdom もコンポーネントの描画テストも用意していない。
**現時点では純粋な関数のテストだけで足りる。** 必要になった時点で足すこと。

## やること

まず**最小限**から始める。網羅率を上げるより、中核が守られていることが大事。

### 優先度1: `src/lib/game-logic.ts` の連鎖開放

既存テストは触りだけなので、**連鎖開放（BFS）を厚くすること。**
ここが一番壊れやすく、壊れたときに一番気づきにくい。

- 部分的にしか広がらない盤面（壁で区切られた領域）
- 盤面の端・角から開いたとき
- 隣接数が0でないセルを開いたときは1マスだけ開く
- 旗が立っているセルは連鎖に巻き込まれない
- 爆弾を踏んだとき `exploded` になり、連鎖しない

`resetExplodedCell` と `countFlags` も未カバー。

### 優先度2: `src/lib/ice-colors.ts`

- 45状態すべてがユニークな色になる
- 同じ合計数の色は明度と彩度が一致する（この性質が崩れると設計が壊れる）

### 優先度3: `src/hooks/useGame.ts` の reducer

- スコア計算、スピードボーナス、被弾時のライフ減少、レベルクリアのボーナス

## 完了条件

- 優先度1がすべてカバーされている
- **わざと実装を壊すとテストが落ちることを確認済み**（テストが機能していることの確認）

## 検証

1. `npm run lint` と `npm run build` と `npm test` が通る
2. **書いたテストが本当に機能するか確かめる。**
   対象のロジックをわざと壊し、テストが落ちることを確認してから元に戻す。
   落ちないテストは書いていないのと同じ
